# 在线下载完整链路修复方案

日期：2026-09-29。状态：已实施，待真实来源与真机 Instruments 最终验收。

目标：解决在线下载时的重复目录请求和附属文件重复计算，修复取消/恢复/清理的已知缺陷，并验证持续下载、入库期间下载页、在线目录页和资料库列表的滚动表现。

依据：

- [目录复杂度与完整链路诊断](OnlineDownloadDiscoveryComplexityDiagnosis.md)
- [下载任务第三轮 Review](../../Design/DownloadTasks/DownloadPageV1-Review-R3.md)

## 1. 范围与完成条件

已复现、必须修复的五项：

1. 同目录多选歌曲重复完整分页：1,001 首歌曲、3 页目录产生 3,003 次 browse。
2. 附属文件逐曲全量匹配：1,000 首音频及同名歌词的发现阶段约 13 秒，候选检查为 O(音频数 × 附属文件数)。
3. 取消正在等待共享封面的音频，不能及时释放音频工作槽和整次任务。
4. 恢复时远端文件消失，执行器、任务汇总与清理对文件范围的理解不一致。
5. 旧单曲归档后恢复，原始 displayName、duration 和单曲请求信息丢失。

另外三处已经确认存在工作量，但尚未测量卡顿贡献：队列阶段变化的全量投影/持久化、逐曲入库读取全库快照、资料库列表主线程排序/分组及离屏订阅。它们必须完成测量；命中的瓶颈应在本次性能验收前修复。

完成条件包括请求数量、任务行为、运行成本和真实 UI 表现。分段测试通过或某个 MainActor 心跳指标改善，均不能单独作为整个问题已解决的依据。

## 2. 目录发现：每次执行共享一份目录结果与索引

在 AppServices 增加独立的目录发现组件，由下载队列创建每次执行的 `DirectoryDiscoveryContext`。单曲、同目录多选、跨目录多选、递归文件夹、目录与歌曲混选统一调用该组件。

一次执行指一次开始或一次恢复；任务 ID 保持稳定，每次执行使用新的 operationID。缓存跟随 operationID，任务结束/取消后释放，恢复重新读取远端目录。

### 缓存内容与键

- 目录键：来源实例及配置版本、规范化父目录、浏览模式、排序。虚拟根与 Provider 根在边界统一映射。
- 分页键：目录键加 pageSize 和 pageToken。身份/配置版本使用内部标识，不使用凭证或令牌作为缓存键。
- 保存完整目录结果和索引：音频、子目录、按文件名匹配的歌词、目录公共封面。
- 文件名、扩展名与匹配键只计算一次；保留当前大小写不敏感匹配和输出顺序语义，不额外合并本来不同的文件。
- 一份公共封面集合由音频关联引用，避免为每首音频重复解析、排序同一批封面。
- 只保留需要的目录项和索引，避免原始分页、完整目录、每首歌曲候选数组重复占用内存；保留现有目录深度及音频数量限制，并覆盖附属文件造成的内存增长。

### 分页与失败语义

1. 同一执行对每个目录只启动一次完整扫描；访问相同目录的消费者复用同一个扫描结果。
2. 只有全部分页成功且游标检查通过，才将目录标记为完整。空目录的成功结果可以缓存。
3. 分页失败、取消或重复游标不得变成“完整空目录”。共享给当前等待者的失败不触发每首歌曲各自重试；自动重试如有需要，按目录统一且有界执行。
4. 发现中的 UI 数量可以分批发布，但文件删除核对、附属关联和完整目录复用必须等待该目录扫描成功。
5. 已成功的音频恢复时直接保留结果，不再进行无用的附属关联。为发现新增文件或核对远端变化所需的目录扫描仍按上述规则执行。
6. 缓存命中也不能绕过来源访问控制；执行期间来源被禁用、移除或配置发生变化时，旧执行停止，晚到结果不能写入新执行。

请求预算：无故障、无显式重试时，实际目录请求数等于本次需要访问的不同目录的分页数之和，与选中歌曲数量无关。现有 1,001 首样本必须从 3,003 次降为 3 次；目录与其中歌曲混选也保持 3 次。

索引建立和查询的工作量应随目录项及实际关联结果增长；不再逐首遍历全部歌词。若确实有大量公共封面关联，输出量本身仍需计入成本，不宣称所有场景都是严格 O(N)。

### 网络缓存的实施边界

本轮首先落地上述任务缓存，它为下载正确性和请求预算提供确定保证。URLSession HTTP 缓存作为传输层补充。

跨页面、跨任务的短期共享浏览缓存安排在任务缓存验收之后，独立实施和验证。该扩展需要：容量限制、可绕过的刷新策略、来源身份与配置失效、相同请求合并、独立等待取消，以及防止不同时间的分页结果拼成“完整目录”。开始/恢复下载默认获取本轮新目录快照，不依赖共享缓存的 TTL 保证正确性。是否追加该扩展以目录页重复请求的测量收益为依据。

## 3. 共享附属下载：每个消费者独立取消

用共享传输注册表管理同次执行中的封面/歌词下载。键包含 operationID 与来源文件 ID，记录底层传输、消费者和已完成临时文件。

- 音频等待共享传输时登记自己的消费者 ID；取消后立即结束自己的等待，释放音频工作槽。
- 仍有消费者时保留底层传输；最后一个消费者退出时取消底层请求。
- 整次任务取消时，取消该执行的所有消费者及传输；不能影响后续恢复或其他操作。
- 完成、失败与取消竞态只能完成等待者一次；旧回调通过 operationID 检查后才能更新状态。
- 下载完成后的临时文件保留到该执行不再需要；复制期间持有使用权，避免取消或清理与文件复制竞争。
- 可选附属文件失败仍允许音频入库，并保留对应提示。

此处必须分别验证“取消等待者”和“取消底层请求”，不能仅在 `await transfer.value` 返回之后检查取消。

## 4. 恢复、任务汇总与清理使用同一份结果

恢复发现成功后，对该任务旧记录与本次发现结果做一次核对：

| 旧文件/远端情况 | 恢复行为 |
| --- | --- |
| 已成功 | 保留结果，不重复下载 |
| 未成功，仍存在 | 重新排队 |
| 未成功，完整扫描确认已消失 | 标记跳过，原因 `remote_item_missing`；页面显示“源文件已不存在” |
| 目录读取失败或取消 | 保留旧记录，不推断文件已删除 |
| 本次发现新增文件 | 根据原任务范围加入，继续遵守数量限制 |

直接选中文件只有在 Provider 明确返回资源不存在，或对应权威目录完整扫描确实能确认消失时，才应用上述消失语义；认证失败、限流、网络错误不等同于消失。

任务执行终态、汇总计数、恢复能力和“清理已完成”共用同一状态归约规则。存在失败/取消音频时任务可恢复；全部文件已成功或明确跳过时任务可完成，跳过原因仍可查看。附属文件失败与音频失败保持现有不同影响。

旧单曲归档时完整保留原 `OnlineDownloadQueueDownloadTask`，包括 metadataHint、duration、displayName、supportingParentID 和单曲标识。直接恢复与归档后恢复生成相同的入库请求；跨进程持久化仍应兼容旧格式。

清理只移除符合终态规则的任务历史及不再引用的恢复记录，保留已入库媒体。校验清理后重启不恢复已清理历史，也不误删仍在运行任务的共享资源。

## 5. 状态、持久化和 UI 的处理原则

先记录每次阶段发布的耗时、处理文件数、主线程占用与 UI apply 次数，再按热点实施下列修改。

### 队列与持久化

- 保留独立的字节进度流及约 200 ms 节流；高频进度更新只访问对应文件。
- 增加明确的阶段变更信息（taskID、fileID、revision），让 Scene 和页面按受影响条目更新，避免每次遍历全部历史来寻找变化。
- 任务计数在文件阶段迁移时更新；完整汇总用于初次加载、恢复重建与校验。
- 同一批发现结果和连续阶段变化合并发布；取消、失败和最终完成及时送达，不能被合并丢失。
- 将恢复状态的全量投影/编码放到受控后台流程，使用 revision 防止旧保存覆盖新保存；调度合并应发生在昂贵投影之前。
- 如果测量显示主线程的字典写时复制仍是热点，再采用按任务拆分状态或增量持久化更新；不能仅将 JSON 编码移后台便宣称全量状态成本已经解决。
- 取消、清理、关闭等关键边界继续验证 flush 和落盘顺序，不将可恢复性依赖于不可靠的进程退出回调。

### 页面刷新

- 下载页和在线目录页按文件/任务差量更新；进度不重建 section、header 或整表。
- 结构计算和排序使用不可变输入在后台完成，携带 revision；MainActor 应用最新结果，丢弃已过期计算。
- 资料库歌曲列表避免每次入库都在主线程对全部已加载歌曲重新排序、分组。相邻变更合并一次，元数据变化只更新受影响行；结构确实变化时重建必要的 snapshot。
- 页面离屏停止自己的渲染观察，重新出现后读取最新状态。共享 LibraryViewModel 的订阅不能由一个子页面退出时直接停掉，以免影响其他可见页面。
- 渲染任务在让出执行权或等待后台计算之后再次检查取消和 revision；仅调用 `cancel()` 不保证旧渲染不会执行。
- 快速入库期间仍保持滚动位置、当前筛选、任务身份和可见进度正确。

## 6. 入库成本：测量后按受影响数据缩小事务

将真实 `LocalMediaImporter → LibraryPersistenceStore.apply → LibraryChange → UI` 纳入联合探针，分别测量媒体解析、文件移动、事务读取/校验/保存、页面查询排队和刷新耗时。

如果逐曲全库快照是主要瓶颈，优先将事务涉及的歌曲、专辑、资源及引用关系按 ID 查询，校验和清理限定到受影响的关系范围。继续保持事务原子性、引用完整性、去重和回滚；缺乏局部查询依据的复杂事务保留原路径并单独记录。

若需要合并入库提交，必须先定义逐文件结果、取消边界和失败回滚语义，再引入有上限的小批次；不能将整次下载攒成一个巨大事务。并发量暂沿用当前 3 个音频工作槽，任何调高或拆分下载/入库工作槽的决定都应由吞吐与内存测量支持。

元数据自动填充开启/关闭分别测量。自动填充可能在下载任务完成后继续请求、入库和刷新，因此采样持续到其后续工作稳定结束。

## 8. 验收矩阵

### 自动化的确定性断言

| 场景 | 必须满足 |
| --- | --- |
| 1,001 首目录分别选 1/100/501/1,001 首 | 每次冷执行均为 3 次 browse |
| 目录与其中歌曲混选 | 同一目录仍只扫描 3 页；音频不重复注册/下载 |
| 多目录、递归、重叠目录 | 请求数为不同访问目录的实际分页数之和 |
| 取消后恢复 | 新执行重新读取，但每目录仍只扫描一次；已成功音频不重下 |
| 100/500/1,000 首及同名歌词 | 记录索引构建和候选检查次数，排除音频数 × 歌词数的扫描；关联结果与旧语义一致 |
| 分页失败、空目录、重复游标 | 不复用不完整目录，不误判删除；有界失败/重试 |
| 来源配置/授权变化 | 缓存失效，晚到旧结果无权更新新执行 |
| 两首音频共享慢封面 | 取消一首立即结束其等待，另一首继续且封面只下载一次 |
| 最后一个音频等待封面时取消 | 底层请求收到取消，父任务可结束、下一任务可启动，无需封面先返回 |
| 取消与完成同时发生 | 每个等待者恰好完成一次，无旧回调污染恢复任务 |
| 失败文件删除后恢复 | 原始状态、汇总、恢复能力和清理结果一致，显示消失原因 |
| 旧单曲归档、重启、恢复 | 原任务身份及完整 metadataHint 保留 |
| 清理完成历史 | 活跃任务和已入库文件保留，重启不恢复已清理历史 |

### 联合性能验证

用同一 taskID/operationID/fileID/importID 串起请求计数、缓存命中、首个下载时间、进度回调、文件暂存、入库事务、队列发布、持久化和 UI render/apply。性能日志记录计数及内部关联 ID，避免记录凭证、临时下载 URL 等敏感内容。

验证分两级，结果分别报告：

1. 可重复的本地 HTTP fixture + 真实下载实现 + 真实 importer/Store + UIKit，覆盖批量文件、歌词封面、慢速下载、失败重试及已有大资料库。内存 Provider 探针继续用于精确请求预算，但不能代替此集成验证。
2. Release 配置真机及用户实际使用的来源，在下载页、在线目录页、资料库列表持续滚动，采集 Instruments 主线程/卡顿证据。先测同设备、同页面的无下载基线，再测下载、入库和自动填充期间的表现。

报告至少包含：各阶段耗时、最大及分位主线程处理时间、超过 50 ms 的业务主线程工作、滚动长帧、峰值内存、UI 应用次数和后台查询等待。对反复出现且由下载链路引起的长任务逐一解释和修复；帧率结果结合设备刷新率判断。仅减少请求数或后台总耗时不能代替这一验收。

最后一处业务改动后运行受影响的核心、Scene、HTTP/持久化及 UIKit 回归，并完成架构检查与 diff 检查。复用工程 `.noindex/DerivedData` 和已有 `.noindex` 产物目录；不因新一轮测试创建随机 DerivedData。

## 9. 当前状态

### 已完成

1. `OnlineDownloadQueue` 已引入 operation 级目录发现缓存。相同父目录的单曲、多选、文件夹递归和混选共享完整分页结果；歌词与封面在目录扫描时一次建索引，不再逐曲全量匹配。
2. 共享附属下载以 `(operationID, itemID)` 隔离，消费者可以独立取消；最后一个消费者取消时底层传输随即取消，音频工作槽和后续任务不再等待慢封面返回。
3. 恢复时会核对完整目录扫描结果。失败文件确认从远端消失后标记为 `remote_item_missing` 并显示“源文件已不存在，已跳过”；全部成功或明确跳过的任务进入不可恢复终态并可清理。
4. 旧单曲归档保留完整下载请求、`metadataHint`、`duration`、`displayName` 和父目录信息，归档后恢复与直接恢复生成相同入库请求。
5. 队列持久化变更按 200ms 合并，终态立即保存；下载页、Scene 和在线目录结构刷新按 100ms 合并，单文件字节进度仍独立更新。
6. 资料库歌曲页离屏后停止页面级观察和渲染任务；排序、分组、字幕映射和 diffable snapshot 在后台准备，并用 revision 丢弃晚到结果。
7. `LibraryPersistenceStore` 缓存 actor 内业务库与本地图谱快照，单条记录持久化改为定向查询。普通连续入库在提交后增量回填缓存；专辑合并、图谱替换和删除使用失效重建路径，并保留原子提交、回滚及图谱清理语义。

### 测量结果

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 同目录选择 1,001 首，3 页 | 3,003 次 browse，约 11,799ms | 3 次 browse，约 37ms |
| 目录与其中 2 首歌曲混选 | 9 次 browse | 3 次 browse |
| 1,000 首音频与同名歌词 | 逐曲扫描，约 13,008ms | 4 次 browse，一次索引，约 91ms |
| 1,000 首音频、无歌词 | 未单独记录旧耗时 | 2 次 browse，约 30ms |
