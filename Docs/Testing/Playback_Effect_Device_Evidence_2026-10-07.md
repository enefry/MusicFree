## 体验差异与剩余问题

1. **自然换歌与播放/暂停采用不同策略。** 视频出现 `als → Fun → mpc8` 的自动衔接。当前 gapless 准备下一首时使用零 overlap，C render 在存在已准备下一首时跳过通常的尾部 fade，接收下一首也不重新启动单曲淡入。单曲渐变用于开始/恢复、软暂停/停止和手动替换；自动换歌渐变由 crossfade 设置控制。当前 crossfade=false，故自动换歌不会得到 3 秒叠加渐变。此行为与当前开发文档一致；不能直接把缺少换歌渐变归因于设置保存失败。
2. **暂停反馈与实际输出不同步。** 视频在“已暂停”状态将时间标签停在 0:06，而音频还在完成 3 秒淡出；恢复时标签到 0:09。这与引擎立即发布暂停意图、渐变期间继续消耗 PCM 的实现相符，界面应区分正在淡出和已经停止输出，避免让用户以为暂停未响应。改变暂停/过渡状态契约需要保留再次点击恢复的意图处理。
3. **末次自动换歌有低电平区间，成因尚未确认。** 约 25–26 秒几乎静音，26–28 秒电平仍较低。缺少该 `mpc8` 原始文件的对照，不能认定这是引擎新产生的静音，也不能直接沿用此前其他 Musepack 样本的源静音结论。源节点包络日志是全局控制包络，不足以独立测量逐首源内容和最终输出。
4. **真实 UIKit 约束冲突。** 日志包含 96 组 `Unable to simultaneously satisfy constraints`。例如播放器进度区第 43–60 行：slider 20 + timeStack 24 + spacing 4 = 48，却强制父高度 52。列表第 2819–2836 行：44 高的内容加上下各 8 的 inset 需要 60，但行的 encapsulated height 是 52。另有折叠状态下固定高度约束冲突。它们可能影响布局和交互表现，不能据此认定音频包络停止执行。
5. **其他控制台信息的界限。** 顶部 Telegram/Bazel 替换路径和 `swift_debug_settings.py` 路径错误属于调试器模块/源码映射诊断；同一记录随后有正在运行的 MusicFree 节点和完整 render 包络。两条 unsafeForcedSync、一条音频 session 主线程警告、RealMedia 索引警告也需要独立调用栈或源文件证据，不能单凭警告将其定为本次听感根因。

## 当前结论

本次用户设备材料确认了播放/暂停/恢复的 3 秒渐变执行，并指出自然换歌设置与界面暂停反馈的体验差异。均衡器仅验证了平直参数；交叉淡化没有开启，未完成交叉淡化真机验证。自动换歌的低电平区间和 UIKit 冲突保留为待处理问题，未将整套播放效果标记为已修复。
