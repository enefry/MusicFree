# MusicFree iOS 歌曲与歌曲集合菜单交互约定

> 当前状态：统一动作模型和主要列表交互已实现；原生双指多选仍需要真实手势验收。

## 目标

Review 并统一 iOS 中所有歌曲行和歌曲集合列表的 context menu，参考 Apple Music iOS 的紧凑列表交互，同时保留项目已经确定的产品要求：

- 长按歌曲直接打开原生 context menu，不依赖“编辑 -> 多选 -> 删除”。
- 收藏、分享、删除/移除位于原生菜单第一行。
- 歌曲集合列表使用 `UICollectionView` 原生双指滑动多选。
- 不使用自定义弹窗模拟 context menu。

参考图为 Apple Music iOS 播放历史列表。图中展示的是列表行内快捷操作，不是长按菜单截图，因此两层交互需要分别实现：

1. 行内快捷操作：收藏按钮、`...` 更多入口、播放时间和紧凑歌曲行。
2. 原生 context menu：长按歌曲，或点击 `...` 后展示同一套原生 `UIMenu` 动作。

## 覆盖范围

### 歌曲行列表

- 所有歌曲。
- 收藏。
- 专辑、艺人、流派、文件夹详情中的歌曲。
- 搜索结果中的歌曲。
- 播放历史。
- 播放列表详情。

### 歌曲集合卡片列表

- 专辑。
- 艺人。
- 流派。
- 文件夹。

集合卡片菜单与歌曲行菜单分开建模，不能把歌曲专属的收藏动作强行放到专辑、艺人或流派菜单中。

## 统一歌曲菜单

所有歌曲行共享同一套动作来源和顺序，避免原生 context menu、行内 `...` 菜单和其他入口发生漂移。

### 第一行快捷动作

使用 UIKit 原生 `UIContextMenuConfiguration`、`UIMenu` 和 `UIAction`，通过 palette/inline menu 呈现：

1. 收藏或取消收藏。
2. 分享。
3. 删除或移除。

删除/移除使用原生 destructive 属性；收藏使用 checked state；不可用动作使用 disabled 属性。动作图标使用 SF Symbols。

### 普通菜单动作

按以下顺序统一提供：

1. 播放。
2. 查看歌曲详情。
3. 下一首播放。
4. 加入队列。
5. 添加到播放列表。

长按和 `...` 入口必须调用同一套动作构造逻辑。播放历史的行内收藏按钮直接执行收藏，不需要先打开菜单。

## Apple Music iOS 播放历史对齐

播放历史按参考图保留紧凑的歌曲行结构：封面、歌曲名、艺人/附加信息、播放时间，以及右侧行内收藏按钮和 `...` 更多入口。

- 右上角 `Clear` 保留为页面级“清除播放历史”操作。
- 行内 `...` 使用原生 `UIMenu`，与长按菜单共享动作模型。
- 菜单中的“删除”改为“从播放历史移除”，只删除历史记录，不删除资料库原曲。
- 页面级“清除播放历史”继续使用确认流程，并明确说明歌曲仍保留在资料库中。
- 播放历史不因增加 context menu 而引入编辑模式删除流程。

## 删除语义

- 所有歌曲、收藏、专辑/艺人/流派/文件夹详情：删除表示从资料库删除歌曲或集合对应的资料库内容，沿用现有确认和错误处理。
- 播放历史：删除表示移除历史记录；需要使用历史专用 repository/service API，不能复用资料库删除 API。
- 播放列表详情：删除显示为“从播放列表移除”，只移除当前歌单关系，资料库原曲保留。
- 用户创建的播放列表卡片：删除播放列表仍属于集合卡片菜单或页面操作，不与歌曲行删除混淆。

## 歌曲集合与原生双指多选

集合卡片列表统一使用 `UICollectionView` 原生多选能力：

- 通过 collection view 的原生多选配置和 selection callbacks 驱动状态。
- 双指滑动直接进入多选，不添加自定义双指手势覆盖 UIKit 行为。
- 选择过程中隐藏单项 context menu，显示原生选择状态和批量操作栏。
- 处理快速滑动、跨行、跨 section、分页加载、数据源刷新和最后一个项目，不能依赖不完整的可见 cell 集合计算选择结果。
- 多选结束后一次性发布最终 selection，避免中间回调导致漏选。
- 现有编辑模式可保留为兼容入口，但删除不再依赖编辑模式。

歌曲列表若需要支持相同的双指多选，也统一迁移到共享的 UIKit collection view 容器；播放列表详情的编辑模式继续承担拖动排序，但歌曲移除必须同时支持长按菜单。

## 集合卡片菜单

集合卡片使用原生 `UIContextMenu`，动作按对象能力提供：

- 分享。
- 播放。
- 下一首播放。
- 加入队列。
- 添加到播放列表。
- 适用时的删除或移除。

集合对象不显示歌曲收藏动作。分享动作不再由外层自动插入到不明确的位置，而是由统一集合菜单模型明确控制第一行和顺序。

## 实施边界

- 复用 `LibraryTracksViewController`、`LibraryCollectionsViewController`、`LibraryCollectionDetailViewController` 和现有队列动作服务。
- 播放历史和播放列表详情统一使用 UIKit 原生歌曲行容器，不再依赖已移除的 SwiftUI `List` 或页面桥接。
- 只修改菜单、多选、列表行交互和所需的历史删除接口；保留现有未提交的其他功能修改。
- 本计划只针对 iOS，不以 macOS Music 的菜单或布局为参考。

## 验证计划

### 自动化

- 对所有歌曲行入口验证长按后出现原生 context menu。
- 验证收藏、分享、删除/移除在菜单第一行且同一水平区域。
- 验证长按删除不需要进入编辑模式。
- 验证播放历史删除不会删除资料库歌曲。
- 验证播放列表删除只移除歌单关系。
- 验证集合卡片菜单动作和歌曲菜单动作没有错误混用。

### iOS 模拟器与手动验收

- 在当前 iPhone 模拟器运行 UI 测试并保存截图。
- 手动执行真实双指滑动，覆盖同一行、跨行、快速滑动、跨 section 和分页边界。
- 对照 Apple Music 参考图检查播放历史：行高、封面尺寸、右侧收藏/`...`、播放时间、`Clear` 位置和底部空白。
- 检查专辑、艺人、流派、文件夹仍保持正常多列布局，列表底部无异常大块空白。
- 检查双指选择没有中间漏选，且批量操作栏显示的数量与实际选中项目一致。

## 明确假设

- Apple Music 参考图确认的是 iOS 播放历史的行内快捷操作，不是 context menu 内部截图。
- 因此行内收藏按钮和 `...` 入口必须保留，但它们与长按原生 context menu 共享动作模型。
- “删除”在不同上下文按对象语义解释，不使用一个会误删资料库的通用删除实现。
- 本次实现完成后再以真实 iOS 模拟器截图和手动双指操作作为最终验收依据。
